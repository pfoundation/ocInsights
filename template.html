Definitions and limits

A session tree is a top-level session plus every subagent session it spawned. The tree's turns are your prompts on the parent; its edits and its shipping come from the whole tree. Turns to ship is all your turns over judged sessions divided by shipped sessions, so an unshipped session's turns count against its model. Steer share is the share of your turns after the first in each session; one-shot is shipped sessions that needed a single turn. A tree is judged when it edited and at least one edit had a recorded path — question-answering and abandoned sessions with no edits are excluded outright, which is what keeps few-turn failures from looking good.

Task size confounds the per-session view (thirty turns for a feature beats two for a typo), so the toggle reads turns per 10 shipped edits instead. Era and selection confound both: models were used in different months with different tooling, and harder tasks went to stronger models. Under a plan-vs-build split, tree outcomes ride with the build phase, so plan rows are mostly unjudged. The radar normalises each axis across the ranked groups shown, so it compares those groups to each other, not to any absolute scale. The shaded half holds the three primary axes — turns to ship, ship rate, edits per turn — and the core score is their mean, 0 to 100. Dollars per shipped tree sits last and is never primary.

How to read this, and what it cannot tell you

Output is every edit, write or patch tool call, attributed to the session's dominant model — the one signal opencode recorded consistently across versions. Line counts stopped after 1.15.13 on June 5 and appear only as a supplementary column. The default view groups by model family and pairs the model that dominated each session's plan phase with the model that dominated its build phase, labelled plan → build. Set role to off for per-model output; the build-sessions-only scope applies there, because explore, plan and librarian sessions read by design and would make any model used for exploring look unproductive. Sessions are attributed to the model that produced most of their replies; 96% have one model at 80% or more.

Selection bias is real and not removable: heavy models get hard tasks, cheap models get lookups. Models were also used in different eras with different tooling. Read this as how each model performed in the work you actually gave it, not as a benchmark. Zero-cost entries were served on plans that record no per-token cost; they sit in the left band and are excluded from the per-dollar view. Dashed lines are medians.

Definitions and limits

Verified counts a session once if any shell command matched a build, test, type-check or lint tool (pnpm build, tsc, vitest, jest, pytest, go test, eslint, biome, ruff and similar). Shipped means the session's edits landed in one of your commits within @@ship_days@@ days; it is judged only for sessions whose edit paths were recorded, so the column is blank for OpenAI providers, which never record them. Edit failures are edit or write tool calls that returned an error. Edits per file is edits divided by distinct files touched; it is blank where the provider did not record file paths. Bars in the table are scaled to the column maximum among the rows shown.

Same caveats as the productivity map: the default view pairs planner with builder by family, sessions attributed to their dominant model, and the model you chose for a task depended on the task. The build-sessions-only scope applies when role is off.

How attribution works, and where it is soft

A commit's window runs from the previous commit in the same repository to the commit itself, capped at 72 hours, with 5 minutes of grace after. Sessions whose recorded edits inside the window touch files in the commit share it in proportion to how many of its files each touched. Sessions that edited in the window but never had a file path recorded (OpenAI providers, and the gap before the edit ledger) fall back to a split by active minutes; the summary line reports how many commits used each basis. Prompts per commit credits each session's prompts to the window in proportion to its active time there. Median lines are weighted by attribution share. Fractional commits are summed, so a commit shared by two sessions counts once in total.

Edit paths come from three sources, merged: the message record, the legacy part table for February to August, and an append-only ledger written by a small opencode plugin from September on. The message record still carries paths today; the ledger exists because opencode has already dropped two data sources without notice, and the coverage strip above shows the day it happens again. A commit can still include hand edits made alongside the agent, and a window can contain work for more than one feature. Commit size also varies by repository, which is why lines per commit sits on the map rather than being ignored. Scope defaults to all session types because exploring and planning are part of shipping; the commit is what closes the loop.

MethodHow the numbers are made

Judgment calls

Four decisions every number on this deck depends on.

Active hours are a heartbeat: each user or assistant message credits min(gap to the previous one, 10 min), and the first credits 60 s. Idle overnight contributes nothing.

A session is attributed to the model that produced most of its replies. 96% have one model at 80% or more. Model ids are canonicalised first; nothing is bucketed as other.

Output is file edits: every edit, write or patch tool call. Line counts stopped being written after 1.15.13 on 5 June and appear only as a supplementary column.

A commit is credited to the sessions whose recorded edits touched files in it, weighted by files touched. Sessions that were active but touched none of those files advised only and get no credit.

Caveats that do not go away

Selection bias is real: heavy models get hard tasks, cheap models get lookups. Models were used in different eras with different tooling. A commit can include hand edits made alongside the agent, and a window can hold more than one feature. Read every per-model number as how this model performed on the work it was given, not as a benchmark.

Cost and token sums come from session records, split across message days by active time. Fresh tokens equal input plus output plus reasoning; cache reads are reported separately because they dwarf the rest. All dates and hours are UTC.
